=== F-017 VERIFICATION EVIDENCE 07: AUTHORIZATION CHECKS ===
Timestamp: 2026-11-23T15:14:15+05:30
Scope: Order creation lifecycle authorization and status immutability on creation

1. Authorization Boundary Enforcement:
- Order lifecycle states: `DRAFT`, `SUBMITTED`, `UNDER_REVIEW`, `APPROVED`, `REJECTED`, `DISPATCHED`, `COMPLETED`, `CANCELLED`.
- Only `ADMIN`, `OWNER`, and authorized management roles hold `order:approve` permission, which transitions `SUBMITTED` -> `APPROVED` via `POST /api/v1/sales/orders/:id/approve` after evaluating ATP inventory and creating atomic stock reservations.
- Order creation endpoint `POST /api/v1/sales/orders` strictly forbids direct specification of `APPROVED`, `DISPATCHED`, or any status other than `DRAFT` or `SUBMITTED`.

2. Tested Roles and Behaviors:
- Salesman role (`salesman1@millledger.local`):
  * Attempt to create order with `status: "APPROVED"` -> HTTP 400 Bad Request.
  * Attempt to create order with `status: "DISPATCHED"` -> HTTP 400 Bad Request.
  * Attempt to create order with `status: "DRAFT"` -> HTTP 201 Created (`order.status: "DRAFT"`).
  * Creation without status parameter -> HTTP 201 Created (`order.status: "SUBMITTED"`).
- Admin role (`admin@millledger.local`):
  * Attempt to create order with `status: "APPROVED"` directly in creation body -> HTTP 400 Bad Request. Admins must also pass through the approval workflow to ensure ATP stock reservations are transactionally created.
- Verified in `server/src/orders.test.ts` (Test 4) and `server/src/modules/sales/sales.service.ts:333-346`.
