=== F-017 VERIFICATION EVIDENCE 10: EXPECTED VS ACTUAL ===
Finding ID: F-017
Title: Unvalidated `status` in order creation payload allows salesman to set `status: "APPROVED"` directly in PostgreSQL
Severity: P0
Category: Authorization / Mass Assignment / Privilege Escalation
Status: VERIFIED-PASS

[Item 1: Mass Assignment Prevention on Order Creation Route]
- EXPECTED (REQ-026, OWASP API3:2023): HTTP POST /api/v1/sales/orders must restrict client-supplied status to DRAFT or SUBMITTED, rejecting APPROVED or other post-approval lifecycle statuses with HTTP 400.
- ACTUAL: `createOrderSchema` updated to `status: z.enum([OrderStatus.DRAFT, OrderStatus.SUBMITTED]).optional()`. Submitting `status: "APPROVED"` returns HTTP 400 Bad Request.
- DELTA: None.

[Item 2: Domain-Level Service Guard]
- EXPECTED: `salesService.createOrder` must enforce domain invariant that new orders can only enter in DRAFT or SUBMITTED status.
- ACTUAL: `sales.service.ts:333-346` checks `input.status` and throws `AppError("New sales orders can only be created with DRAFT or SUBMITTED status", 400)` if any other status is supplied.
- DELTA: None.

[Item 3: Downstream Stock Reservation Invariant]
- EXPECTED: No orders can enter the database as APPROVED with 0 stock reservations.
- ACTUAL: Orders can only become APPROVED via `approveOrder()`, which performs atomic ATP inventory checks and inserts reservations into `stock_reservation`. Invariant 3, 4, and 10 hold with 0 violations.
- DELTA: None.

[Item 4: Regression Test Coverage]
- EXPECTED: Automated test asserting that salesman and admin cannot submit `status: "APPROVED"`, invalid statuses are blocked, DRAFT is accepted, and omitting status defaults to SUBMITTED.
- ACTUAL: Added in `server/src/orders.test.ts` (Test: `F-017: blocks mass assignment of status in sales order creation payload (OWASP API3:2023)`). 4/4 tests pass.
- DELTA: None.
