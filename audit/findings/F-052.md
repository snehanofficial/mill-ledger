# F-052: Unassociated Form Labels and Missing Accessible Names Across Operational Forms

- **ID**: F-052
- **Title**: Unassociated Form Labels and Missing Accessible Names Across Operational Forms
- **Severity**: P1
- **Category**: Accessibility / Form Semantics / WCAG AA Failure
- **Standard refs**: WCAG 2.2 SC 1.3.1 (Info and Relationships - Level A), SC 3.3.2 (Labels or Instructions - Level A), SC 4.1.2 (Name, Role, Value - Level A)

---

## 1. Expected vs Actual

- **EXPECTED (WCAG 2.2 SC 1.3.1, 3.3.2, 4.1.2)**:
  Every user input control (`<input>`, `<select>`, `<textarea>`) must have a programmatically determined accessible name, either via `<label htmlFor="...">` matching the input's `id`, wrapping the input with `<label>`, or setting `aria-label`/`aria-labelledby`.
- **ACTUAL (evidence: `client/src/pages/orders-page.tsx:827-882`, `client/src/pages/production-page.tsx:520-677`, `client/src/pages/purchases-page.tsx:336-444`, `client/src/pages/payments-page.tsx:865-940`, `client/src/pages/dispatch-page.tsx:440-513`, `audit/evidence/a11y/snapshots/ADMIN_en_orders.json`)**:
  Across all core operational data entry forms, visual labels are rendered as detached, unlinked `<label>` elements without `htmlFor`, and inputs/selects are rendered without `id`:
  ```tsx
  {/* orders-page.tsx:826-834 */}
  <div className="flex flex-col gap-1.5">
    <label className="text-xs font-semibold text-muted-foreground">
      Customer
    </label>
    <select
      value={selectedCustomerId}
      onChange={(e) => setSelectedCustomerId(e.target.value)}
      className="..."
    >
  ```
  ```tsx
  {/* orders-page.tsx:874-882 */}
  <label className="text-xs font-semibold text-muted-foreground">
    Order quantity (pkts)
  </label>
  <input
    type="number"
    value={orderQuantity}
    onChange={(e) => setOrderQuantity(Number(e.target.value))}
    className="..."
  />
  ```
  Neither `htmlFor` nor `id` is specified. In the browser accessibility tree, these form fields have an accessible name of `null` or `""`.
- **DELTA**:
  Over 30 operational input fields (Customer, Product, Quantity, Order Notes, Supplier, Inventory Item, Unit Cost, Vehicle Number, Driver Contact, Payment Amount, Payment Mode) have no programmatic label association.

---

## 2. Impact

- **Who is hurt**: Screen reader users (who hear only "Combobox, collapsed" or "Edit text, blank" without knowing what field they are on) and speech input users (who cannot say "Click Customer" or "Click Order quantity" because the control lacks an accessible name matching the visual label).
- **Operational consequence**: High risk of incorrect order, batch, or payment submissions on the shop floor.

---

## 3. Repro Steps & Root Cause

### Repro Steps
1. Navigate to `/orders` and open "New sales order".
2. Open Chrome DevTools -> Elements -> Accessibility panel.
3. Select the `<select>` element for customer or the `<input type="number">` for quantity.
4. Inspect "Computed Properties" -> "Name": Observe `Name: ""`.

### Root Cause
Components authoring used visual-only styling without adhering to accessible form patterns (no `htmlFor` on `<label>` and no matching `id` on `<input>`).

---

## 4. Recommended Fix & Regression Test

### Recommended Fix
Assign explicit IDs and `htmlFor` attributes to every form field, or wrap them using the existing `@/components/ui/field` primitive:
```tsx
<div className="flex flex-col gap-1.5">
  <label htmlFor="order-customer" className="text-xs font-semibold text-muted-foreground">
    Customer
  </label>
  <select id="order-customer" name="customerId" ...>
</div>
```

### Regression Test
Automate via Playwright DOM evaluation: assert that all `input`, `select`, and `textarea` elements have `hasAccessibleName === true` (`element.labels.length > 0 || element.getAttribute('aria-label') !== null`).
