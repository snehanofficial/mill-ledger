## Delta
When an outbox record encounters a JavaScript runtime exception (such as `TypeError: Cannot read properties of undefined (reading 'map')` or invalid JSON line format), `err.response?.status` is undefined. The catch handler incorrectly categorizes this internal client exception as a transient `NETWORK_ERROR`, resets the corrupt order status back to `"queued"`, and executes `break`. Because orders are processed in strict `createdAt` sequence, **the corrupt order permanently remains at the head of the queue**, causing every subsequent sync attempt to crash on the first item and immediately abort. All subsequent valid orders are permanently prevented from syncing to the server.

---

## Impact
- **Who is hurt**: All mobile salesmen collecting customer orders in the field.
- **How**: If a single order is corrupted due to app storage migration, partial write, or null items array, the salesman's entire offline terminal becomes permanently frozen. Hundreds of valid orders accumulated during a sales shift will never sync to the factory, stalling order fulfillment and invoicing.

---

## Repro Steps
1. Insert an outbox record with missing `items` into IndexedDB (`items: undefined`).
2. Insert 3 valid customer orders behind it in the outbox.
3. Call `processOutbox(userId)`.
4. Observe: The corrupt order is re-saved with `status: "queued"`, and the loop breaks.
5. Re-run `processOutbox(userId)`: The loop again encounters the corrupt order, fails, and breaks.
6. The 3 valid customer orders remain in `queued` status indefinitely and are never transmitted to the server.

---

## Root Cause
- File: [`client/src/offline/sync-engine.ts`](file:///home/snehan/projects/web/mill-ledger/client/src/offline/sync-engine.ts#L254-L277)
  - `catch` block assumes that any error where `err.response?.status` is falsy must be a transient network issue.
  - Client runtime validation errors (malformed payload, missing lines array, undefined object properties) are treated as transient network failures rather than terminal validation conflicts, causing infinite head-of-line blocking.

---

## Recommended Fix (Do Not Apply)
1. Add strict schema validation using Zod (`offlineOrderSchema.safeParse(order)`) before constructing the API payload.
2. If client validation fails or `err.response` is absent while `err instanceof TypeError`, set `status = "failed"` or `"conflict"` with `lastErrorCode = "CLIENT_VALIDATION_ERROR"`.
3. Do not `break` on client schema corruption; quarantine the bad item and continue processing subsequent orders in the queue.
