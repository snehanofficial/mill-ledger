# Finding F-009: Missing Database-Level Immutability Enforcement for Stock Movements and Sales Invoices

**ID**: F-009  
**Title**: Application database role retains full UPDATE and DELETE privileges on stock movements and posted invoices without database triggers or rules  
**Severity**: P1  
**Category**: Security / Data Integrity / Audit Trail  
**Standard Refs**: MLD Core Rule (Never overwrite stock balances; preserve immutable posted invoices), OWASP ASVS v4.0.3 Item 8.3.1, REQ-009, REQ-036  
**Status**: OPEN  

---

### Expected (source)
Under [MASTER_PROJECT_PLAN.md](file:///home/snehan/projects/web/mill-ledger/MASTER_PROJECT_PLAN.md), [business-rules.md](file:///home/snehan/projects/web/mill-ledger/docs/business-rules.md), and [product-requirements.md](file:///home/snehan/projects/web/mill-ledger/docs/product-requirements.md) REQ-009 / REQ-036:
"Never overwrite stock balances. Use traceable, transactional stock movements. Preserve immutable posted invoices and production records; use corrections or reversals."
Audit requirements mandate that database-level controls (e.g. `BEFORE UPDATE OR DELETE` triggers or revoked privileges) must prevent modification or deletion of posted movements and invoices even if application code is compromised or a developer connects via SQL.

### Actual (evidence links)
In the throwaway database migrated via Prisma:
1. `information_schema.role_table_grants` confirms the application database role (`postgres`) holds full `INSERT`, `SELECT`, `UPDATE`, `DELETE`, `TRUNCATE` privileges on both `stock_movement` and `sales_invoice`.
2. `pg_trigger` contains 0 user-defined triggers across all tables in public schema.
3. In `/audit/scripts/verify-immutability.ts`, raw SQL `UPDATE` and `DELETE` queries executed successfully on both tables without database resistance:
   - `UPDATE stock_movement SET quantity = 999 WHERE id = ...` succeeded (`UPDATE 1`).
   - `DELETE FROM stock_movement WHERE id = ...` succeeded (`DELETE 1`).
   - `UPDATE sales_invoice SET totalAmount = 9999 WHERE id = ...` succeeded (`UPDATE 1`).
   - `DELETE FROM sales_invoice WHERE id = ...` succeeded (`DELETE 1`).
4. Log output: [/audit/evidence/immutability-check.txt](file:///home/snehan/projects/web/mill-ledger/audit/evidence/immutability-check.txt).

### Delta
Immutability is purely an application-layer convention. The database engine does not enforce immutability; any SQL injection, rogue admin script, or direct DB session can silently alter or delete posted stock movements and invoices.

### Impact
Regulatory non-compliance with Section 130 of the CGST Act (tampering with invoices and records). A malicious actor or bug can wipe ledger movements or forge invoice values without audit log trail.

### Repro Steps
1. Connect via psql: `psql $DATABASE_URL`.
2. Run: `UPDATE "stock_movement" SET "quantity" = 0 WHERE id = (SELECT id FROM "stock_movement" LIMIT 1);`
3. Observe: PostgreSQL executes `UPDATE 1` with 0 errors.

### Root Cause
Prisma migrations only create tables, indexes, and simple foreign keys; no PostgreSQL trigger functions (`RAISE EXCEPTION 'Posted stock movements are immutable'`) or REVOKE statements are included in `server/prisma/migrations/`.

### Recommended Fix (do not apply)
Add a PostgreSQL migration creating a trigger function that rejects `UPDATE` and `DELETE` on `stock_movement` and on `sales_invoice` where `status = 'POSTED'`.

### Regression Test to Add
`audit/tests/db-immutability.test.ts` executing raw SQL UPDATE/DELETE against `stock_movement` and expecting SQL error `P2010` / trigger exception.
