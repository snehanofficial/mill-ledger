# F-078: Missing Express Response Compression Middleware and Unconfigured PostgreSQL Connection Pool

- **ID**: F-078
- **Title**: Missing Express Response Compression Middleware and Unconfigured PostgreSQL Connection Pool
- **Severity**: P2
- **Category**: Server Performance / Network Overhead & Resource Pooling
- **Standard Refs**:
  - RFC 9110 (HTTP Semantics: Compression & Content-Encoding)
  - Node-Postgres Connection Pooling Best Practices

---

## Expected (Source)
- **Source**: Phase 10 Audit Prompt & Specification (`audit/01-expected-spec.md` REQ-055).
- Enterprise REST API servers must serve responses with HTTP gzip or brotli compression to minimize egress bandwidth, and configure PostgreSQL connection pools with bounded concurrency (`max`, `idleTimeoutMillis`, `connectionTimeoutMillis`) tuned for production load.

---

## Actual (Evidence Links)
- **Evidence**:
  - Code inspection: [`server/src/app.ts`](file:///home/snehan/projects/web/mill-ledger/server/src/app.ts#L20-L40).
    Middleware chain includes `helmet()`, `cors()`, `express.json()`, but completely lacks `compression()`.
  - HTTP curl observation: A request to `/api/v1/reports/sales?organizationId=cmwnfu9g300003mabr2uqrelp` returned an uncompressed payload of **2,907,717 bytes (2.9 MB)** with no `Content-Encoding` header.
  - Database pool inspection: [`server/src/db/client.ts`](file:///home/snehan/projects/web/mill-ledger/server/src/db/client.ts#L6-L9):
    ```ts
    const pool = new pg.Pool({
      connectionString: env.DATABASE_URL,
    });
    ```
    `pg.Pool` defaults to `max: 10`, `connectionTimeoutMillis: 0` (unlimited wait), and `idleTimeoutMillis: 10000`.

---

## Delta
1. Response compression is not enabled on the API server. In a production deployment without an external reverse proxy (e.g. Nginx/Cloudflare), large JSON arrays (reports, customer listings, invoices) consume 5x to 10x more network bandwidth and take 4x longer to transfer.
2. The PostgreSQL connection pool is unconfigured with default 10 connections. When 50 concurrent requests hit the API simultaneously, 40 requests queue up on the event loop with `connectionTimeoutMillis: 0`, leading to connection pool exhaustion and request timeouts (109 timeouts observed in autocannon report).

---

## Impact
- **Who is hurt**: All users accessing reports and list views from remote mill locations with constrained internet uplinks.
- **How**: Slow data transfers, unnecessary network egress bandwidth consumption, and cascading connection timeouts when concurrency exceeds 10.

---

## Repro Steps
1. Send request with `Accept-Encoding: gzip`:
   `curl -i -H "Accept-Encoding: gzip" http://127.0.0.1:4000/api/v1/reports/sales?organizationId=...`
2. Observe HTTP response headers lack `Content-Encoding: gzip`.
3. Check response size is ~2.9 MB instead of ~300 KB.

---

## Root Cause
- Files: [`server/src/app.ts`](file:///home/snehan/projects/web/mill-ledger/server/src/app.ts), [`server/src/db/client.ts`](file:///home/snehan/projects/web/mill-ledger/server/src/db/client.ts).
  - Package `compression` is not installed or added to the Express middleware stack.
  - `pg.Pool` options are left at unconfigured defaults.

---

## Recommended Fix (Do Not Apply)
1. Install and register `compression` middleware in `server/src/app.ts`:
   ```ts
   import compression from "compression";
   app.use(compression({ threshold: 1024 }));
   ```
2. Configure `pg.Pool` in `server/src/db/client.ts`:
   ```ts
   const pool = new pg.Pool({
     connectionString: env.DATABASE_URL,
     max: 25,
     connectionTimeoutMillis: 5000,
     idleTimeoutMillis: 30000,
   });
   ```
