# F-073: Mobile 4G Largest Contentful Paint (LCP) Budget Violation on Authenticated Routes

- **ID**: F-073
- **Title**: Mobile 4G Largest Contentful Paint (LCP) Budget Violation on Authenticated Routes (3.4s - 4.0s vs 2.5s Target)
- **Severity**: P1
- **Category**: Frontend Performance / Core Web Vitals
- **Standard Refs**:
  - Google Core Web Vitals: Largest Contentful Paint (LCP < 2.5s Good, 2.5s-4.0s Needs Improvement)
  - W3C Web Performance Working Group

- Under simulated mobile conditions (4x CPU slowdown, slow 4G throttling), the Largest Contentful Paint (LCP) across key application routes (Login, Dashboard, Order Capture, Reports) must be under **2.5 seconds**.

## Delta
While the unauthenticated `/auth/login` page easily passes at 1.1s, all three core authenticated routes fail the 2.5s threshold by up to 58%:
- `/dashboard`: 3.39s (36% over budget)
- `/orders`: 3.95s (58% over budget, borderline poor)
- `/reports/sales`: 3.53s (41% over budget)

Root mechanism of the delay:
On authenticated routes, a sequential waterfall prevents the LCP element from rendering:
1. Download 824 KB of initial JS over 4G (~1.0s).
2. Execute React and evaluate Better Auth session check via `/api/auth/get-session` (~0.8s under 4x CPU).
3. Fetch the lazy route chunk (e.g. `orders-page-*.js`) dynamically (~0.4s).
4. Fetch page domain data (e.g. `/api/v1/sales/orders`) (~0.8s).
5. Render table and trigger LCP paint (~0.5s).
Total time before LCP paint reaches 3.4s - 4.0s.

---

## Impact
- **Who is hurt**: Field salesmen and factory supervisors on mobile data networks.
- **How**: Long perceived load times and blank/skeleton waiting states before actionable data appears on screen.

## Root Cause
- Files: [`client/src/app.tsx`](file:///home/snehan/projects/web/mill-ledger/client/src/app.tsx), [`client/src/layouts/authenticated-layout.tsx`](file:///home/snehan/projects/web/mill-ledger/client/src/layouts/authenticated-layout.tsx)
  - Cascading serial waterfall: Shell auth check blocks route chunk loading, which blocks API data fetching.
  - Large initial JS bundle delays initial hydration.
  - Absence of route prefetching or SSR/streaming.

---

## Recommended Fix (Do Not Apply)
1. Parallelize session check with route chunk loading or prefetch route chunks when authenticated session token cookie exists.
2. Reduce initial bundle size per F-072.
3. Optimize API payload sizes (server pagination per F-074) so data responses arrive in < 100ms.
