## Expected (Source)
- **Source**: `Problem_Statement_Winter_Internship_Application_2026.md`, `audit/01-expected-spec.md` (REQ-055, REQ-064).
- The API backend must handle multi-user enterprise load reliably. Key list endpoints must be paginated, execute in bounded time (< 500ms p95), and never crash or exhaust server memory when handling 50 concurrent requests against realistic mill production scale (10,000 orders).

---

## Actual (Evidence Links)
- **Evidence**:
  - Code inspection: [`sales.service.ts`](file:///home/snehan/projects/web/mill-ledger/server/src/modules/sales/sales.service.ts#L616-L665).
  - Single request observation: A single `GET /api/v1/sales/orders` request with 10,000 orders took **4.49 seconds** and produced **21,343,842 bytes (21.3 MB)** of JSON.
  - Load test execution: Running `autocannon -c 50 -d 30` against `/api/v1/sales/orders` triggered an immediate Node.js crash:
    `FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory` (Process exit code 134).
  - Background task crash log: `audit/evidence/performance/load-test/orders.json` and task-142 log.

---

## Delta
Instead of a scalable, paginated query returning bounded records within milliseconds, `getSalesOrders` executes an unpaginated `prisma.salesOrder.findMany` followed by a nested `for` loop over all orders and all order lines, calling `await this.getAvailableStock(...)` for each line. At 10,000 orders with 1 line each, this executes **20,001 SQL queries** in a single request. Under 50 concurrent requests, the server attempts to execute 1,000,000 queries, exhausts the 2GB V8 heap, and terminates the entire Node.js server.

---

## Impact
- **Who is hurt**: All users across all factory roles (Super Admin, Salesmen, Floor Supervisors, Accountants).
- **How**: Complete Denial of Service (DoS). When any user opens the Orders screen with large transaction history, the entire ERP server crashes for everyone until process supervisor restarts it.
- **Cost**: Total mill shutdown; field salesmen unable to submit orders; factory dispatches blocked.

---

## Root Cause
- File: [`server/src/modules/sales/sales.service.ts`](file:///home/snehan/projects/web/mill-ledger/server/src/modules/sales/sales.service.ts#L616-L665)
  - Missing `take` / `skip` / cursor pagination on `prisma.salesOrder.findMany`.
  - Nested N+1 loop executing `getAvailableStock()` serially per line per order instead of aggregating stock availability in a single batch query.

---

## Recommended Fix (Do Not Apply)
1. Add mandatory server-side cursor or offset pagination (`take: Math.min(limit, 100)`, `skip`) to `sales.routes.ts` and `sales.service.ts`.
2. Remove the inline `getAvailableStock` loop from list queries. Shortage calculation should either be computed on-demand for individual order detail views, or computed via a single batch SQL join on active stock reservations.
