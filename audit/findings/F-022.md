# Finding F-022: Absence of Audit Logging Across Operational Mutations and Administrative Actions

**ID**: F-022  
**Title**: `auditService.log` is invoked only on report exports; zero audit log records are generated for orders, dispatches, production runs, invoices, or payments  
**Severity**: P1  
**Category**: Security Logging & Monitoring / Non-Repudiation  
**Standard Refs**: OWASP Top 10:2021 A09:2021 (Security Logging and Monitoring Failures), OWASP ASVS v4.0.3 Section 8.2 (Audit Logging Requirements), REQ-050  

---

## Expected (Source)
Source: [docs/reporting-audit.md](file:///home/snehan/projects/web/mill-ledger/docs/reporting-audit.md), [docs/product-requirements.md](file:///home/snehan/projects/web/mill-ledger/docs/product-requirements.md) REQ-050, OWASP ASVS Section 8.2.1.  
All security-relevant and business-critical operations must be recorded in an immutable audit log table (`audit_log`), capturing: `userId`, `action` (CREATE, UPDATE, APPROVE, DISPATCH, REVERSE, POST), `entity` (SalesOrder, ProductionRun, Dispatch, SalesInvoice, Payment), `entityId`, `timestamp`, `details` (metadata / changes), and `ipAddress`.

---

## Actual (Evidence Links)
Evidence: Static code audit of `server/src` working tree:
```sh
git grep -n "auditService.log" server/src/
```
Output:
```text
server/src/modules/reporting/reporting.routes.ts:167: await auditService.log({
server/src/modules/reporting/reporting.service.ts:950: await auditService.log({
```
Across all modules in `server/src/modules/`:
- `sales.service.ts`: 0 calls to `auditService.log` (No audit log on order create, update, approve, reject).
- `dispatch.service.ts`: 0 calls to `auditService.log` (No audit log on physical dispatch posting).
- `production.service.ts`: 0 calls to `auditService.log` (No audit log on run drafting, posting, or reversal).
- `finance.service.ts`: 0 calls to `auditService.log` (No audit log on tax invoice creation or credit note issue).
- `payment.service.ts`: 0 calls to `auditService.log` (No audit log on recording cash/cheque/NEFT payments).
- `inventory.service.ts`: 0 calls to `auditService.log` (No audit log on purchase receipt posting).

The only time `auditService.log` is invoked is when an authorized user downloads a report export in CSV or JSON format (`GET /api/v1/reports/:report/export`).

---

## Delta
The application contains an `audit_log` PostgreSQL model and an `AuditService` implementation, but it is effectively dead code for 95% of the ERP system. No operational or administrative mutations are ever logged.

---

## Impact
- **Forensic Failure & Repudiation**: If fraudulent stock movements, fake orders, or improper invoice cancellations occur, administrators have zero audit logs in PostgreSQL to determine which user account or IP executed the transaction. Statutory GST audit trails cannot be verified.

---

## Repro Steps
1. Perform an order creation and approval flow via API or UI.
2. Query PostgreSQL: `SELECT count(*) FROM audit_log WHERE entity = 'SalesOrder';` -> returns 0.
3. Post a dispatch, create an invoice, or record a ₹10,000 payment.
4. Query PostgreSQL: `SELECT count(*) FROM audit_log WHERE action IN ('CREATE', 'APPROVE', 'POST');` -> returns 0.

---

## Root Cause
- Operational services (`sales.service.ts`, `production.service.ts`, `finance.service.ts`, `payment.service.ts`) do not inject or invoke `auditService.log` in their transactional methods.

---

## Recommended Fix
1. Integrate `auditService.log` into each domain transaction across sales, production, inventory, and finance.
2. Log user ID, IP address, timestamp, document numbers, and previous/new status values.

---

## Regression Test to Add
Add tests across `orders.test.ts`, `invoice-dispatch.test.ts`, and `payments.test.ts` asserting that mutations increase `prisma.auditLog.count()` by 1 with expected action and entity attributes.
