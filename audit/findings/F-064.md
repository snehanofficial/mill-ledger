# Finding F-064: Disabled Buttons Set `pointer-events: none`, Suppressing `cursor: not-allowed` and Inspection

- **ID**: F-064
- **Title**: Disabled Buttons Set `pointer-events: none`, Suppressing `cursor: not-allowed` and Tooltip Inspection
- **Severity**: P2
- **Category**: Accessibility / Feedback Patterns
- **Standard Refs**:
  - W3C WCAG 2.2 Success Criterion 4.1.2 Name, Role, Value (Level A)
  - W3C WCAG 2.2 Success Criterion 1.4.13 Content on Hover or Focus (Level AA)
  - Anti-Slop R-39: Accessible Semantics & Interaction Affordances (`disabled controls show cursor: not-allowed`)

---

## Expected Behavior
Per Anti-Slop Rule R-39 and modern interaction affordance standards:
> "Every enabled interactive element shows cursor: pointer, set once in the base CSS layer; disabled controls show cursor: not-allowed."

When a button is disabled, users (especially mouse and screen magnification users) require immediate visual feedback explaining that the control is inoperable (`cursor: not-allowed`) and should be able to hover or focus to view a tooltip explaining *why* the button is disabled (e.g. "Save disabled: form contains validation errors").

---

## Actual Behavior
1. In `client/src/components/ui/button.tsx:8`:
   ```tsx
   const buttonVariants = cva(
     "inline-flex min-h-10 items-center justify-center gap-2 rounded-control border px-4 text-sm font-medium whitespace-nowrap transition-colors outline-none disabled:pointer-events-none disabled:opacity-50 ...",
   ```
2. In `client/src/index.css:186-189`:
   ```css
   button:disabled,
   [aria-disabled="true"] {
     cursor: not-allowed;
   }
   ```
3. Because `button.tsx` applies Tailwind utility `disabled:pointer-events-none`, the browser intercepts and drops all mouse pointer events on disabled buttons. As a result:
   - The browser never computes or renders `cursor: not-allowed`. The pointer remains a standard arrow.
   - Child tooltips (e.g., `<Tooltip><TooltipTrigger asChild><Button disabled ...`) never trigger on hover or focus because pointer events are dead.
   - Screen readers and magnification tools cannot inspect why an action is blocked.
4. Programmatic audit evidence recorded in `audit/evidence/motion/metrics/feedback-patterns-audit.json`:
   - `disabledClasses` contains `disabled:pointer-events-none`
   - `disabledPointerEvents: "none"`
   - `disabledCursor: "not-allowed"` (declared in stylesheet, but unreachable due to `pointer-events: none`).

---

## Delta
`disabled:pointer-events-none` actively breaks the declared `cursor: not-allowed` rule in `index.css` and prevents disabled button tooltips from functioning.

---

## Impact
Users hovering over disabled buttons receive no visual cursor indication that the element is inoperable, leading to confusion as to whether the button is broken or intentionally disabled. Tooltips explaining why an action cannot be performed are completely unreachable.

---

## Repro Steps
1. Navigate to `/showcase#actions`.
2. Locate the button labeled "Disabled".
3. Hover mouse pointer over the button.
4. Observe that the mouse cursor remains a standard default pointer arrow rather than `not-allowed`.
5. Notice that clicking produces no action and hovering triggers no explanation.

---

## Root Cause
- [button.tsx:8](file:///home/snehan/projects/web/mill-ledger/client/src/components/ui/button.tsx#L8)

---

## Recommended Fix
1. Remove `disabled:pointer-events-none` from `buttonVariants` in `client/src/components/ui/button.tsx`.
2. Allow native HTML `<button disabled>` to receive hover pointer events so `cursor: not-allowed` displays properly.
3. For accessible tooltips, wrap disabled buttons in an interactive wrapper element or use `aria-disabled="true"` instead of HTML `disabled` to preserve keyboard focusability.
