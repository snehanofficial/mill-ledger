# Finding F-014: Hardcoded Tax Rates and Unused `TaxRate` Master Table

**ID**: F-014  
**Title**: Statutory GST rates are read from static `product.taxRate` columns; the dedicated `TaxRate` master table is never queried  
**Severity**: P2  
**Category**: Data Architecture / GST Compliance / Master Data  
**Standard Refs**: Section 9 of CGST Act, 2017 (Levy and collection of GST), REQ-006, REQ-034  
**Status**: OPEN  

---

### Expected (source)
According to [data-model.md](file:///home/snehan/projects/web/mill-ledger/docs/data-model.md) and [product-requirements.md](file:///home/snehan/projects/web/mill-ledger/docs/product-requirements.md) REQ-006 / REQ-034:
GST tax rates change over time via GST Council notifications. The system defines a dedicated `TaxRate` entity in `schema.prisma` with `hsnCode`, `rate`, `cgstRate`, `sgstRate`, `igstRate`, `effectiveFrom`, and `effectiveTo`. Tax calculations on orders and invoices must resolve applicable rates from this schedule based on document posting date and HSN code.

### Actual (evidence links)
In the current implementation:
1. `TaxRate` table exists in PostgreSQL and is seeded in `server/prisma/seed.ts:567`.
2. However, across all active server modules (`server/src/modules/sales/`, `server/src/modules/finance/`, `server/src/modules/inventory/`), there is **zero query to `prisma.taxRate` or `tx.taxRate`**.
3. In [sales.service.ts:230](file:///home/snehan/projects/web/mill-ledger/server/src/modules/sales/sales.service.ts#L230):
   `const taxRate = Number(variant.product.taxRate);`
4. In [finance.service.ts:118](file:///home/snehan/projects/web/mill-ledger/server/src/modules/finance/finance.service.ts#L118):
   `const taxRate = Number(line.taxRate);`
5. Rates are statically read from `product.taxRate` without checking effective date schedules.

### Delta
The database has a dead `tax_rate` table. The application cannot handle statutory tax rate revisions with forward or backward effective dates; any rate change requires mutating the product master, which would retroactively corrupt unposted quotes or require ad-hoc overrides.

### Impact
Inability to comply with GST Council rate revisions (e.g. rate changes taking effect at midnight on the 1st of a month). Changing `product.taxRate` affects all future drafts without effective-date boundaries.

### Repro Steps
1. Run `grep -rn "prisma.taxRate\|tx.taxRate" server/src/modules/`.
2. Observe 0 occurrences in module logic.

### Root Cause
`sales.service.ts` resolves rates by looking at `productVariant.product.taxRate` instead of querying `tx.taxRate.findFirst({ where: { hsnCode, effectiveFrom: { lte: date }, ... } })`.

### Recommended Fix (do not apply)
Update `sales.service.ts` and `finance.service.ts` to look up rates from `TaxRate` by item HSN and transaction date, falling back to `product.taxRate` only if no schedule entry exists.

### Regression Test to Add
`audit/tests/tax-rate-effective-date.test.ts` inserting a scheduled 12% rate effective next month and asserting current invoices use 5% while next month's invoices use 12%.
