# Finding F-012: Missing GSTIN Format and Mod 36 Checksum Validation

**ID**: F-012  
**Title**: Absence of format and checksum validation allows malformed and counterfeit GSTIN strings in customer records and tax invoices  
**Severity**: P1  
**Category**: Statutory Compliance / Input Validation / GST Compliance  
**Standard Refs**: Section 25 of CGST Act, 2017, Rule 8 of CGST Rules, 2017, GST Portal Specification (gst.gov.in), OWASP ASVS v4.0.3 Item 5.1.4  
**Status**: VERIFIED  

---

### Expected (source)
Under Rule 8 of CGST Rules, 2017 and official GST portal specifications (gst.gov.in per Rule E5), a Goods and Services Tax Identification Number (GSTIN) is a 15-character statutory identifier with a mandatory format:
- Digits 1-2: 2-digit State code (01 to 37)
- Characters 3-12: 10-character PAN of the business (`[A-Z]{5}[0-9]{4}[A-Z]{1}`)
- Character 13: 1-character entity code (`[1-9A-Z]`)
- Character 14: Default character `'Z'`
- Character 15: 1-character check digit computed via Luhn Mod 36 algorithm.
According to REQ-002, REQ-034, and REQ-063, any entered customer GSTIN must be validated for both regex format AND check digit before accepting it or snapshotting it onto posted tax invoices.

### Actual (evidence links)
There is **zero** GSTIN validation in:
- Backend schemas and routes: `server/src/modules/sales/sales.routes.ts`, `finance.routes.ts`.
- Shared contracts: `shared/src/schemas/`.
- Frontend forms: `client/src/pages/customers-page.tsx`.
- Database constraints: `schema.prisma` and PostgreSQL `chk` constraints.

In `/audit/scripts/verify-gstin.ts`, the database accepted completely invalid GSTINs without error:
- `"INVALID-GSTIN-123"` -> Customer created (ID `cmwnhqb8u00002mabtuj0wz7q`).
- `"33INVALID"` -> Customer created (ID `cmwnhqb9500012mabf9i5x3f0`).
- `"99ZZZZZ9999Z9Z9"` (invalid state code 99) -> Customer created.
- `"000000000000000"` -> Customer created.
- `"SHORT"` -> Customer created.
- Evidence log: [/audit/evidence/gstin-validation.txt](file:///home/snehan/.gemini/antigravity/brain/1cab6c78-831c-4338-9deb-799e7cee4d7f/.system_generated/tasks/task-195.log).

### Delta
Any arbitrary garbage string is accepted as a GSTIN, snapshotted onto posted statutory invoices, and included in GSTR-1 outward supply reports (Table 4 B2B supplies).

### Impact
Invoices issued with invalid GSTINs cannot be reconciled by the buyer, preventing buyer Input Tax Credit (ITC) claims under Section 16(2) of the CGST Act. Inward reports on the GST portal fail JSON schema validation.

### Repro Steps
1. Execute `pnpm --filter @mill-ledger/server exec tsx ../audit/scripts/verify-gstin.ts`.
2. Observe all 5 invalid GSTIN customer inserts succeed without validation failure.

### Root Cause
No Zod validation schema or utility function exists for GSTIN format or Mod 36 checksum in `shared/` or `server/`.

### Recommended Fix (do not apply)
Implement a shared Zod schema `gstinSchema` in `@mill-ledger/shared`:
1. Regex: `^[0-9]{2}[A-Z]{5}[0-9]{4}[A-Z]{1}[1-9A-Z]{1}Z[0-9A-Z]{1}$`.
2. Checksum validator implementing the standard Luhn Mod 36 check digit algorithm.

### Regression Test to Add
`audit/tests/gstin-validator.test.ts` testing 20 valid benchmark GSTINs and 30 invalid variants (bad state code, invalid PAN structure, wrong check digit).
