# Finding F-015: Concurrent Double-Submit Race Condition on Idempotency Keys Throws 500 Unique Constraint Error

**ID**: F-015  
**Title**: Idempotency pre-query race condition causes concurrent duplicate submissions to crash with unhandled 500 unique constraint error  
**Severity**: P2  
**Category**: API Resilience / Concurrency / Idempotency  
**Standard Refs**: RFC 7231, OWASP API Security Top 10:2023 API10:2023, REQ-051  
**Status**: OPEN  

---

### Expected (source)
Under [offline-sync.md](file:///home/snehan/projects/web/mill-ledger/docs/offline-sync.md) and [product-requirements.md](file:///home/snehan/projects/web/mill-ledger/docs/product-requirements.md) REQ-051:
When an offline PWA client or browser client retries or double-submits a request with the same `idempotencyKey`, the server must guarantee exactly-once processing and return the existing resource cleanly (HTTP 200/201), even when identical requests arrive concurrently.

### Actual (evidence links)
In [sales.service.ts:105-125](file:///home/snehan/projects/web/mill-ledger/server/src/modules/sales/sales.service.ts#L105-L125):
```typescript
if (input.idempotencyKey) {
  const existing = await tx.salesOrder.findUnique({
    where: { idempotencyKey: input.idempotencyKey },
    ...
  });
  if (existing) {
    return { order: existing, shortages: [] };
  }
}
```
The implementation uses a check-then-act pattern:
1. When two identical requests arrive simultaneously with the same `idempotencyKey`, both execute `findUnique()` concurrently.
2. Neither sees the record yet (as neither has committed).
3. Both proceed to `tx.salesOrder.create()`.
4. One transaction commits; the other crashes with PostgreSQL unique constraint error:
   `Unique constraint failed on the constraint: sales_order_idempotencyKey_key` (Prisma error P2002).
5. The API error handler intercepts this as an unexpected error and responds with **HTTP 500 Internal Server Error**.
- Observed Evidence: Recorded in [/audit/evidence/idempotency-race-condition.txt](file:///home/snehan/projects/web/mill-ledger/audit/evidence/idempotency-race-condition.txt).

### Delta
Instead of returning the existing record idempotently, concurrent double submissions crash with HTTP 500, causing mobile offline sync queues to mark the sync operation as failed and enter an unrecoverable conflict state.

### Impact
Field salesmen experiencing poor network connectivity double-tap the "Submit Order" button; one tap creates the order, but the second tap receives a 500 error, leading the salesman to believe the order failed.

### Repro Steps
1. Execute `pnpm --filter @mill-ledger/server exec tsx ../audit/scripts/verify-idempotency.ts`.
2. Observe `Promise.all([createSalesOrder, createSalesOrder])` with the same key throws `P2002: Unique constraint failed on sales_order_idempotencyKey_key`.

### Root Cause
[sales.service.ts:105-125](file:///home/snehan/projects/web/mill-ledger/server/src/modules/sales/sales.service.ts#L105-L125) relies on a pre-select without catching P2002 on collision or using an advisory lock / `INSERT ... ON CONFLICT DO NOTHING`.

### Recommended Fix (do not apply)
Wrap the transaction in a try-catch for Prisma error code `P2002` on `idempotencyKey`, fetching and returning the existing record if a unique collision occurs during concurrent execution.

### Regression Test to Add
`audit/tests/concurrency-idempotency.test.ts` running 5 simultaneous requests with the same idempotency key and asserting all 5 return the same order ID with HTTP 200/201.
