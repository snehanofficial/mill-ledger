# Finding F-030: Absence of Input Validation Schema on Sales Order Modification Endpoint `PUT /api/v1/sales/orders/:id`

**ID**: F-030  
**Title**: Order modification endpoint lacks request body schema validation, accepting unvalidated mutations and crashing with HTTP 500 on malformed status values  
**Severity**: P0  
**Category**: Input Validation / Data Integrity / Application Crash  
**Standard Refs**: OWASP Top 10:2021 A03:2021 (Injection), OWASP API Security Top 10:2023 API3:2023 (Broken Object Property Level Authorization), OWASP ASVS v4.0.3 Sec 5.1.1, Sec 5.1.4  
**Status**: OPEN  

---

### Expected (source)
Under [architecture.md](file:///home/snehan/projects/web/mill-ledger/docs/architecture.md) and [api-contract.md](file:///home/snehan/projects/web/mill-ledger/docs/api-contract.md), all mutating HTTP endpoints must validate request parameters, bodies, and data types against strict Zod schemas before routing payloads to underlying domain services. Invalid property types, malformed enumerations, and unauthorized properties must be rejected with HTTP 400 Bad Request and detailed field-level errors.

### Actual (evidence links)
In [sales.routes.ts:170-199](file:///home/snehan/projects/web/mill-ledger/server/src/modules/sales/sales.routes.ts#L170-L199), the handler for `PUT /orders/:id` does not invoke any Zod schema:
```typescript
// PUT /api/v1/sales/orders/:id - Update draft order
salesRouter.put(
  "/orders/:id",
  requireAuth,
  authorize("order", "update"),
  async (req: AuthenticatedRequest, res, next) => {
    try {
      const orderId = Array.isArray(req.params.id)
        ? req.params.id[0]
        : req.params.id;
      if (!orderId) {
        throw new AppError("Order ID is required", 400);
      }

      // Enforce server-side ownership from persistent database record, ignoring client-spoofed body
      if (req.user?.role === "SALESMAN") {
        await salesService.getSalesOrderById(orderId, req.user);
      }

      const updated = await salesService.updateDraftOrder(
        orderId,
        req.body,
        req.user!,
      );
      res.json({ status: "updated", order: updated });
    } catch (err) {
      next(err);
    }
  },
);
```
`req.body` is cast to `Partial<CreateOrderInput>` without validation. In [sales.service.ts:764-766](file:///home/snehan/projects/web/mill-ledger/server/src/modules/sales/sales.service.ts#L764-L766), the service attempts:
```typescript
status: input.status
  ? (String(input.status).toUpperCase() as OrderStatus)
  : order.status,
```
When invalid status values (such as `{ "status": 12345 }` or `{ "status": "INVALID_STATE" }`) are submitted, Prisma throws a `PrismaClientValidationError` which crashes the unhandled error middleware, returning HTTP 500 and leaking full stack traces and internal database schemas. Furthermore, raw unsanitized notes and HTML/script payloads are written directly into PostgreSQL.

Observed in live fuzzing test [/audit/evidence/fuzz-results.json](file:///home/snehan/projects/web/mill-ledger/audit/evidence/fuzz-results.json):
```json
{
  "endpoint": "/api/v1/sales/orders/cmwnn4hx70004i6ab83x2j3v7",
  "method": "PUT",
  "vector": "INVALID_STATUS_ENUM",

  "is500": true,
  "leaksPrismaError": true,
  "responsePreview": "{\"error\":\"Internal Server Error\",\"message\":\"\\nInvalid `prisma.salesOrder.update()` invocation..."

```

### Delta
Expected HTTP 400 Bad Request with Zod schema field validation errors. Actual behavior is an unhandled 500 crash with stack trace leakage when invalid data types or enum strings are submitted, and silent acceptance of arbitrary properties without schema controls.

### Impact
Callers can crash server instances, corrupt order lifecycle states, inject arbitrary unstructured notes, and trigger unhandled Prisma errors exposing database metadata.

### Repro Steps
1. Authenticate as an authorized user (Salesman or Admin).
2. Obtain the ID of a `DRAFT` sales order.
3. Send an HTTP `PUT` request to `/api/v1/sales/orders/<orderId>` with body `{"status": "NON_EXISTENT_ENUM_VALUE"}`.
4. Observe HTTP 500 response leaking `PrismaClientValidationError` and Node.js call stack.
5. Automated script: `node --env-file=audit/.env.audit server/node_modules/tsx/dist/cli.mjs audit/scripts/verify-fuzzing-mutations.ts`.

### Root Cause
[sales.routes.ts:170-199](file:///home/snehan/projects/web/mill-ledger/server/src/modules/sales/sales.routes.ts#L170-L199) omits `updateOrderSchema.safeParse(req.body)` middleware or in-handler check.

### Recommended Fix (do not apply)
Define an explicit `updateOrderSchema` in `shared/src/schemas/sales.schema.ts`:
```typescript
const updateOrderSchema = z.object({
  notes: z.string().max(500).optional(),
  lines: z.array(...).optional(),
}).strict();
```
Validate `req.body` with `updateOrderSchema.safeParse(req.body)` and reject any manual client attempts to mutate `status` directly via update.
