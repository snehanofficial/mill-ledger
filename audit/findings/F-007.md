# Finding F-007: Concurrency Race Condition in Sales Order Approval Permits 100%+ Oversell of Available Stock

**ID**: F-007  
**Title**: Missing row-level lock in sales order approval allows concurrent orders to exceed ATP stock by over 100%  
**Severity**: P0  
**Category**: Data Integrity / Concurrency / Inventory Ledger  
**Standard Refs**: ACID Consistency, OWASP API Security Top 10:2023 API10:2023 (Unsafe Consumption of APIs / Concurrency), REQ-027  
**Status**: OPEN  

---

### Expected (source)
According to CDI Benchmark Specification item 6, [product-requirements.md](file:///home/snehan/projects/web/mill-ledger/docs/product-requirements.md) REQ-027, and [business-rules.md](file:///home/snehan/projects/web/mill-ledger/docs/business-rules.md), order approval must atomically reserve available-to-promise (ATP) stock. Total active reservations for any SKU must never exceed physical on-hand stock (`sum(active reservations) <= currentStock`). Under concurrent requests, requests exceeding available stock must fail with HTTP 400 Insufficient Stock.

### Actual (evidence links)
In [sales.service.ts:430-465](file:///home/snehan/projects/web/mill-ledger/server/src/modules/sales/sales.service.ts#L430-L465), `approveSalesOrder` executes inside an interactive transaction under PostgreSQL's default `READ COMMITTED` isolation level, but checks ATP stock using plain `tx.inventoryItem.findUnique` and `tx.stockReservation.aggregate` with **no row lock** (`FOR UPDATE`) on either the inventory item or active reservations.

When 30 parallel approval requests for 10 units each competed for 50 available units in `/audit/scripts/verify-concurrency-approve-dispatch.ts`, all 10 iterations produced critical race condition overselling:
- In iteration 1: 11 orders approved, total reserved: 110 units (120% oversell of 50 units).
- In iterations 2-10: 10 orders approved in each run, total reserved: 100 units (100% oversell of 50 units).
- Evidence artifact: [/audit/evidence/concurrency-oversell-dispatch.txt](file:///home/snehan/projects/web/mill-ledger/audit/evidence/concurrency-oversell-dispatch.txt).

### Delta
Instead of serializing on available stock and rejecting all orders once 50 units were reserved (at most 5 approved), concurrent read-modify-write interleaving allowed 10 to 11 orders to approve simultaneously, doubling the commitment beyond warehouse physical inventory.

### Impact
Customer fulfillment failure and severe business reputational damage. Multiple distributors receive order confirmations for stock that does not physically exist. Mill staff would either dispatch empty cartons, default on delivery, or cause floor stockouts.

### Repro Steps
1. Create an inventory item with `currentStock = 50.000000`.
2. Create 30 SUBMITTED sales orders requesting 10 units each (`SO-1` to `SO-30`).
3. Fire 30 simultaneous `approveSalesOrder` requests via `Promise.all`.
4. Query `SELECT SUM("reservedQuantity") FROM "stock_reservation" WHERE status = 'ACTIVE'`. Observe sum is 100-110 units against 50 physical units.
5. Exact automated script: `pnpm --filter @mill-ledger/server exec tsx ../audit/scripts/verify-concurrency-approve-dispatch.ts`.

### Root Cause
In [sales.service.ts:430-455](file:///home/snehan/projects/web/mill-ledger/server/src/modules/sales/sales.service.ts#L430-L455):
```typescript
const invItem = await tx.inventoryItem.findUnique({
  where: { id: line.inventoryItemId },
});
```
Unlike `postDispatch` (which uses `SELECT ... FOR UPDATE`), `approveSalesOrder` uses a non-locking query. Concurrent transactions concurrently read the same uncommitted reservation state.

### Recommended Fix (do not apply)
1. Acquire an exclusive row lock on `inventory_item` using `tx.$queryRaw\`SELECT id FROM "inventory_item" WHERE id = ${line.inventoryItemId} FOR UPDATE\`` at the start of `approveSalesOrder`.
2. Alternatively, perform an atomic update or conditional reservation insert.

### Regression Test to Add
`audit/tests/concurrency-approval.test.ts` executing 30 parallel approvals against a 50-unit stock fixture and asserting `totalReserved <= 50`.
