# Finding F-008: Dispatch Number Collision Under Concurrent Dispatches Crashing with Unique Constraint Violation

**ID**: F-008  
**Title**: Non-atomic `count()` based dispatch sequence generation causes unique constraint crashes on concurrent dispatches  
**Severity**: P0  
**Category**: Data Integrity / Concurrency / Availability  
**Standard Refs**: ACID Concurrency, OWASP API Security Top 10:2023 API10:2023, REQ-031  
**Status**: OPEN  

---

### Expected (source)
Under [architecture.md](file:///home/snehan/projects/web/mill-ledger/docs/architecture.md) and [product-requirements.md](file:///home/snehan/projects/web/mill-ledger/docs/product-requirements.md) REQ-031, physical dispatch operations must be reliable, concurrent, and crash-free. Dispatch document numbers must be assigned atomically without collisions or transaction rollbacks.

### Actual (evidence links)
In [dispatch.service.ts:71-92](file:///home/snehan/projects/web/mill-ledger/server/src/modules/sales/dispatch.service.ts#L71-L92), the dispatch number is computed using a plain count:
```typescript
const count = await tx.dispatch.count({
  where: { organizationId: order.organizationId },
});
const dispatchNumber = `DSP-${new Date().getFullYear()}-${(count + 1).toString().padStart(4, "0")}`;
```
When concurrent dispatch requests execute, multiple transactions count the exact same committed rows, construct the identical `dispatchNumber` string (e.g. `DSP-2026-0002`), and attempt `tx.dispatch.create()`. One transaction succeeds while all parallel transactions crash with:
`Unique constraint failed on the constraint: dispatch_organizationId_dispatchNumber_key` (Prisma error P2002).
- Observed Evidence: In [/audit/evidence/concurrency-oversell-dispatch.txt](file:///home/snehan/projects/web/mill-ledger/audit/evidence/concurrency-oversell-dispatch.txt), 8 out of 10 parallel dispatches crashed with `Unique constraint failed on dispatch_organizationId_dispatchNumber_key`.

### Delta
Instead of smoothly dispatching multiple trucks simultaneously from the factory floor, 80-90% of concurrent dispatch transactions crash with internal server errors (HTTP 500), rolling back warehouse stock movements and blocking dispatches.

### Impact
Warehouse bottleneck. Multiple packing bays cannot dispatch finished goods vehicles concurrently. Drivers and warehouse operators experience 500 errors during peak loading times.

### Repro Steps
1. Create 2 or more APPROVED sales orders.
2. Trigger `dispatchService.postDispatch()` simultaneously using `Promise.all`.
3. Observe all but one dispatch transaction failing with:
   `PrismaClientKnownRequestError: Unique constraint failed on the constraint: dispatch_organizationId_dispatchNumber_key`.
4. Automated script: `pnpm --filter @mill-ledger/server exec tsx ../audit/scripts/verify-concurrency-approve-dispatch.ts`.

### Root Cause
[dispatch.service.ts:71-76](file:///home/snehan/projects/web/mill-ledger/server/src/modules/sales/dispatch.service.ts#L71-L76). `tx.dispatch.count()` is not atomic and does not acquire row locks or use the centralized atomic `sequenceService.getNextSequence()`.

### Recommended Fix (do not apply)
Refactor `dispatch.service.ts` to use `sequenceService.getNextSequence(tx, order.organizationId, "DISPATCH", currentYear.toString())` which employs row-locked UPSERT on `document_sequences`.

### Regression Test to Add
`audit/tests/concurrency-dispatch.test.ts` executing 10 parallel dispatches across distinct approved orders and asserting 100% success with 0 unique constraint collisions.
