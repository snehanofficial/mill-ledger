### Expected (source)
Under [api-contract.md](file:///home/snehan/projects/web/mill-ledger/docs/api-contract.md) and OWASP API8:2023, every HTTP error response must follow a strict, uniform JSON envelope:
```json
{
  "code": "VALIDATION_ERROR",
  "message": "Human-readable description",
  "fieldErrors": { "fieldName": ["specific reason"] },
  "requestId": "req-cuid-or-uuid"
}
```
All PostgreSQL / Prisma exceptions (P2002 unique, P2003 foreign key, P2034 serialization, 40001 deadlock) must be mapped to operational HTTP status codes (400, 409) with sanitized messages. Internal stack traces and table/column names must never be transmitted in HTTP responses. The frontend client must display inline field errors and preserve user input.

### Actual (evidence links)
1. **Server Error Handler Shape**: In [error.middleware.ts:17-66](file:///home/snehan/projects/web/mill-ledger/server/src/middleware/error.middleware.ts#L17-L66), responses are formatted as `{ error: string }`, completely omitting `code`, `fieldErrors`, and `requestId`:
```typescript
if (err instanceof AppError) {
  res.status(err.statusCode).json({
    error: err.message,
  });
  return;
}
```
2. **Postgres Violations Unhandled**: Foreign key constraint violations (`P2003`) are unhandled in `errorHandler`. When an invalid foreign key is submitted, Prisma throws `PrismaClientKnownRequestError`, which falls through to line 61:
```typescript
res.status(500).json({
  error: "Internal Server Error",
  ...(env.NODE_ENV !== "production"
    ? { message: err.message, stack: err.stack }
    : {}),
});
```
This returns HTTP 500 and exposes full table names, constraint names, and Node.js file paths.
3. **Payload Too Large Crashes 500**: `PayloadTooLargeError` from Express `body-parser` is not an instance of `AppError`, causing 1 MB requests to crash as HTTP 500 with stack traces leaked (verified in 13 out of 13 endpoints in [/audit/evidence/fuzz-results.json](file:///home/snehan/projects/web/mill-ledger/audit/evidence/fuzz-results.json)).
4. **Client UI Error Masking**: In [orders-page.tsx:307](file:///home/snehan/projects/web/mill-ledger/client/src/pages/orders-page.tsx#L307), the client attempts to read `err.response?.data?.message`:
```typescript
toast.error(err.response?.data?.message || "Failed to create order");
```
Because the server returns `{ error: "..." }` and NOT `{ message: "..." }`, `err.response?.data?.message` is permanently `undefined`. The user only ever sees `"Failed to create order"`, masking all server validation messages. Furthermore, zero form fields display inline field errors, and the UI has no component to render `requestId`.

Observed in live audit test [/audit/evidence/error-envelope-results.json](file:///home/snehan/projects/web/mill-ledger/audit/evidence/error-envelope-results.json).

### Delta
Zero uniform error envelope. Complete absence of `requestId` and `fieldErrors`. Stack trace leakage on 413 and foreign key errors. Total masking of server errors in client UI toasts.

### Impact
1. Security: Attackers discover internal database schema, model names, and file directory layout via leaked stack traces.
2. Usability: End-users cannot determine why an order or invoice failed because the UI toast displays only a generic fallback message.
3. Supportability: Users and support staff cannot correlate client failures with backend logs due to missing `requestId`.

### Root Cause
[error.middleware.ts](file:///home/snehan/projects/web/mill-ledger/server/src/middleware/error.middleware.ts) formats errors ad-hoc without an RFC 7807 envelope structure, and [orders-page.tsx:307](file:///home/snehan/projects/web/mill-ledger/client/src/pages/orders-page.tsx#L307) reads mismatched property `message` instead of `error`.

### Recommended Fix (do not apply)
1. Standardize `errorHandler` to emit `{ code, message, fieldErrors, requestId }`.
2. Map `P2003` to HTTP 400 Bad Request with `"Referenced record does not exist"`.
3. Map `PayloadTooLargeError` to HTTP 413 Payload Too Large.
4. Update client `apiClient` interceptor and form components to display `fieldErrors` inline.
